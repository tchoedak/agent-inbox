# agent-inbox: integration guide for coding agents

You are reading this because you are building or changing something that produces a report on a
schedule. This document tells you how to deliver that report into `agent-inbox` so the human can
read it, instead of leaving it as a file they have to remember to open.

This guide is printed by `agent-inbox agent-guide`. It is always current for the installed version.

## When this applies

Wire a producer into the inbox when **all** of these hold:

- It produces output a human is meant to read - a report, digest, summary, dashboard export,
  scan result, or status roll-up.
- It runs on a recurring trigger - cron, launchd, systemd timer, a CI schedule, a scheduled
  agent routine, or any "run this every day" arrangement.
- The output is a file or can be written to one.

Do **not** wire in: logs, metrics streams, one-off scripts a human runs interactively and watches,
build artifacts, or anything nobody reads.

If the user explicitly asks to wire something into agent-inbox, do it regardless of the above.

## The command

```sh
agent-inbox emit --topic <slug> --artifact <path>[:<role>]
```

That is the whole required surface. One call per report. Everything else is optional.

A realistic call from a daily job that produces both a browser report and a terminal-readable one:

```sh
agent-inbox emit \
    --topic trading-perf \
    --title "Daily trading performance" \
    --cadence daily \
    --source-project "$PWD" \
    --artifact report.md:terminal \
    --artifact report.html:primary
```

### Arguments

| Flag | Notes |
| --- | --- |
| `--topic` | Required. The recurring thing this report *is*. Normalized to a slug and created on first use. |
| `--artifact` | Required, repeatable. `path` or `path:role`. `-` reads one artifact from stdin. |
| `--bucket` | Grouping key, default today. Pass `YYYY-MM-DD` only to backfill an older date. |
| `--timestamp` | RFC 3339. Defaults to now. |
| `--title` | Human-readable topic name. Applied on every emit; last write wins. |
| `--cadence` | `daily`, `weekly`, `hourly`, or `none`. Lets the inbox notice when a report stops arriving. |
| `--summary` | One line, written by the producer. Not generated by you at wire-up time. |
| `--tag` | `key=value`, repeatable. |
| `--run-id` | Ties the edition back to the run that made it. |
| `--source-project` | Path of the producing project. |
| `--stdin-name` | Filename for the artifact read from stdin. Required when using `-`. |

### Roles

Each artifact has a role. It is inferred from the extension, and you override it with `path:role`.

- `terminal` - rendered directly in the reader. Inferred for `.md`, `.markdown`, `.txt`, `.text`.
- `primary` - the canonical report, opened in a browser. Inferred for `.html`, `.htm`.
- `data` - supporting data, never shown as the main view. Inferred for `.csv`, `.json`, `.tsv`,
  `.yaml`, `.yml`.

Any other extension **must** name its role explicitly, or the emit fails.

**If the producer emits HTML, strongly prefer also emitting a markdown rendition tagged
`terminal`.** The reader is a terminal, and converting HTML at read time loses layout that lives in
CSS - stat tiles and card headers flatten into unreadable stacks. A producer that already has the
report as structured data can usually render markdown in well under a hundred lines. Both artifacts
go in the same call and become one edition.

## Choosing a topic name

The topic is the recurring thing, not the individual report.

- Good: `trading-perf`, `job-scrape`, `frontier-radar`, `nightly-security-scan`.
- Bad: `report`, `daily`, `output`, `perf-report-2026-08-13` (that is a date, not a topic).

Names normalize, so `trading_perf`, `Trading Perf`, and `trading-perf` are one topic. But
`trading-perf` and `trading-perf-daily` are two, and the inbox will warn that they look alike
without merging them.

**Before inventing a name, check what already exists:**

```sh
agent-inbox topics
```

Reuse an existing topic if this producer is emitting the same recurring report. A new name forks
the history, and history is the point.

## Where to put the call

Put it where the report is finished, in the producer itself - not in a wrapper script and not in the
crontab. The crontab is the wrong place because a human editing the schedule should not be able to
silently detach delivery from production.

**Shell:**

```sh
set -euo pipefail          # so a failed emit fails the job
python generate_report.py --out report.html
agent-inbox emit --topic my-report --artifact report.html
```

**Python:**

```python
subprocess.run(
    ["agent-inbox", "emit", "--topic", "my-report",
     "--artifact", str(path), "--cadence", "daily"],
    check=True,            # never swallow a delivery failure
)
```

**Piping content without writing a file first:**

```sh
generate_digest | agent-inbox emit --topic my-digest --artifact -:terminal --stdin-name digest.md
```

## Rules that matter

1. **Never swallow the failure.** `emit` exits non-zero and explains itself on stderr. Use
   `check=True`, `set -e`, or an explicit status check. A silently skipped delivery means a report
   that quietly stops arriving and nobody notices for a month.
2. **One call per report.** All artifacts of one report go in a single `emit`. Two calls make two
   editions and the second supersedes the first.
3. **Do not pass `--bucket` for a normal run.** It defaults to today. Pass it only to backfill.
4. **Reruns are safe.** Emitting again for the same bucket supersedes and keeps the old revision.
   You do not need to guard against double delivery.
5. **Do not write into the store yourself.** The layout is documented and readable, but writes go
   through the binary because atomicity depends on one owner.
6. **Set `--cadence`** whenever the schedule is known. Without it the inbox cannot tell the
   difference between a report you have not read and a report that never arrived.

## Backfilling history

If the producer already has past reports sitting in a directory, offer to backfill them. A topic
whose history starts today is a poor version of a feature whose entire point is history.

```sh
for f in reports/report-*.html; do
    date=$(basename "$f" .html | sed 's/report-//')
    agent-inbox emit --topic my-report --bucket "$date" --artifact "$f"
done
```

## Verify before you claim it works

Do not report success on the strength of having edited the code. Run the producer, or emit one real
artifact by hand, then confirm:

```sh
agent-inbox topics                     # the topic exists, with the title and cadence you set
agent-inbox editions --topic <slug>    # the edition landed in the right bucket
```

If `agent-inbox` is not installed, say so plainly rather than writing calls to a binary that is not
there. Installation is `cargo install --path .` from the agent-inbox checkout.
